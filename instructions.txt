AI SQL Analyst
1. Product Overview
Product name

QueryPilot — AI-powered natural-language database analyst.

One-line description

A conversational AI application that allows users to query relational databases using natural language, automatically understands database schemas, detects ambiguity in user requests, asks targeted clarification questions when necessary, generates safe SQL, executes it, and explains the results.

Core principle

The application must not behave as a simple:

English → SQL

translator.

Instead:

Natural Language
       ↓
Intent Understanding
       ↓
Schema Retrieval
       ↓
Ambiguity Detection
       ↓
 ┌───────────────┐
 │               │
Ambiguous       Clear
 │               │
 ▼               ▼
Clarification   SQL Generation
 │               │
 └───────┬───────┘
         ▼
    SQL Validation
         ↓
    Safe Execution
         ↓
   Result Analysis
         ↓
   Natural Language
      Response
2. Problem Statement

Many users need to extract information from databases but do not know SQL.

Traditional database interfaces require users to understand:

tables
columns
joins
aggregation
filtering
grouping
SQL syntax

LLM-based text-to-SQL systems solve part of this problem, but naïvely converting natural language directly into SQL creates another problem:

Natural language is often ambiguous.

For example:

"Find the best customer."

Possible interpretations include:

highest total spending
most orders
most products purchased
highest average order value
most recent activity

The system must not guess silently.

It should identify the ambiguity and ask the user to clarify.

3. Goals
Primary goals

The application must:

Allow users to query databases using natural language.
Automatically discover database schemas.
Support a built-in sample e-commerce database.
Support user-provided databases.
Detect ambiguous natural-language queries.
Ask targeted clarification questions.
Generate SQL only after sufficient intent is known.
Validate generated SQL before execution.
Restrict execution to safe read-only operations.
Execute queries against the appropriate database.
Explain results in natural language.
Maintain conversational context.
Support follow-up questions.
Be deployable as a public web application.
Have a clear separation between frontend, backend, AI orchestration and database execution.
4. Non-Goals

The first version should not attempt to:

support every database engine
modify production databases
execute arbitrary INSERT, UPDATE, DELETE, DROP, etc.
automatically expose local databases to the internet
train a custom LLM
build a full BI dashboard platform
replace database administrators
guarantee semantic understanding of every possible business term

11. Schema Knowledge Layer

Do not send the complete database contents to the LLM.

The LLM should receive:

Schema metadata
+
Relevant tables
+
Relevant relationships
+
Business definitions

It should never receive the entire database simply to answer a query.

For large schemas:

User Query
    ↓
Schema Retrieval
    ↓
Relevant tables
    ↓
LLM

Example:

User:

"Who spent the most?"

Relevant schema:

customers
orders

No need to provide unrelated tables such as:

employees
suppliers
warehouse_locations
audit_logs
12. Business Semantic Layer

Support optional descriptions for tables and columns.

Example:

orders.total_amount:
  description: Final amount paid by the customer

orders.status:
  completed: Successfully fulfilled order
  cancelled: Cancelled before fulfilment

revenue:
  definition: Sum of completed order amounts

This is important because database schemas alone don't always encode business meaning.

14. Intent Representation

The LLM should first generate a structured intent representation.

Example:

User:

"Find the best customer."

Internal representation:

{
  "entity": "customer",
  "operation": "ranking",
  "metric": null,
  "time_range": null,
  "limit": 1,
  "sort_direction": "descending",
  "ambiguities": [
    {
      "field": "metric",
      "reason": "The word 'best' has multiple possible meanings."
    }
  ]
}

The application should not generate SQL yet.

15. Ambiguity Detection

This is a core feature.

The system must identify ambiguity in:

Metrics

"best customer"

Possible meanings:

highest spending
most orders
most products purchased
highest average order value
Time

"sales this year"

Potential meanings:

calendar year
financial year
last 12 months
Entity

"Apple sales"

Could refer to:

Apple company
Apple product
Apple brand
Aggregation

"average customer spending"

Could mean:

average total spending per customer

versus other interpretations.

Threshold

"expensive products"

What qualifies as expensive?

price > ₹10,000
price > average price
top 10%
Business terminology

"revenue"

Could require the database owner's definition.

16. Clarification Engine

When ambiguity exists, the application must not guess.

Instead it should generate a concise clarification.

Example:

What do you mean by "best customer"?

1. Highest total spending
2. Most orders placed
3. Most products purchased
4. Highest average order value

The frontend should render these as clickable options.

[ Highest spending ]
[ Most orders ]
[ Most products ]
[ Average order value ]

The user can also provide their own interpretation.

17. Clarification Rules

The clarification engine should:

ask only when ambiguity materially changes the SQL/result
avoid unnecessary questions
group related ambiguities where possible
provide concrete options
allow free-text responses
remember previous answers
never silently choose a potentially different interpretation

Bad:

Please clarify.

Good:

When you say "best customer", should I rank customers by total spending, number of orders, or number of products purchased?

18. Multi-Turn Conversation

The application must maintain conversation state.

Example:

User:
Find the best customer.

AI:
Best based on what?

User:
Total spending.

AI:
For which period?

User:
This year.

AI:
[Result]

Then:

User:
What about the second one?

The system should understand:

same metric
same time period
same entity
rank = 2

It should not start from scratch.

19. Follow-Up Queries

Support contextual queries:

Show the top 5 customers by spending.

Only from India.

Now show their average order value.

What about last year?

Show the second highest.

The system should modify the previous query intent rather than regenerate context blindly.

20. SQL Generation

Only generate SQL after intent is sufficiently specified.

Example:

SELECT
    c.id,
    c.name,
    SUM(o.total_amount) AS total_spending
FROM customers c
JOIN orders o
    ON c.id = o.customer_id
WHERE o.status = 'completed'
GROUP BY c.id, c.name
ORDER BY total_spending DESC
LIMIT 1;

The generated SQL must be based on the actual discovered schema.

Never assume table/column names.

21. SQL Validation

Before execution, run SQL through a validation layer.

Validate:

Syntax

Is it valid SQL for the selected database engine?

Schema

Do tables exist?

Do columns exist?

Permissions

Does the connected user have access?

Safety

Reject:

DROP
DELETE
UPDATE
INSERT
ALTER
TRUNCATE
CREATE
GRANT
REVOKE

For V1, allow only:

SELECT
WITH

Potentially allow:

EXPLAIN

under controlled conditions.

22. Query Cost Protection

Prevent expensive accidental queries.

Implement:

maximum execution time
maximum returned rows
query timeout
pagination
result-size limit

For example:

Maximum execution time: 10 seconds
Maximum rows: 1,000

The application should not allow:

SELECT *
FROM huge_table;

to return millions of rows.

28. Database Connection Security

Never store raw database passwords in plaintext.

For V1:

keep credentials only for the active session
use encrypted transport
do not log credentials
redact credentials from errors
use connection pooling carefully
disconnect idle sessions

For production architecture, credentials should be encrypted at rest if persistent connections are supported.

29. Important Localhost Limitation

If a user chooses:

PostgreSQL
Host: localhost
Port: 5432

from the public website, that means:

User's browser
localhost

not your backend server.

Therefore a deployed backend cannot directly access the user's local PostgreSQL database.

The product must clearly explain:

Local databases cannot be accessed directly by the cloud application. Use the SQLite upload option, connect a publicly reachable PostgreSQL database, or run the application locally.

Do not attempt to bypass this restriction.

33. LLM Structured Outputs

All AI components should preferably return structured JSON rather than free-form text.

For example:

{
  "status": "ambiguous",
  "intent": {
    "entity": "customer",
    "operation": "ranking"
  },
  "clarification": {
    "question": "What should 'best' mean?",
    "options": [
      "Highest total spending",
      "Most orders",
      "Most products purchased"
    ]
  }
}

This makes the application deterministic enough for a production-style backend.

34. Error Handling

The system must handle:

Invalid SQL
I couldn't generate a valid query for this request.
Unknown table
I couldn't find a table representing "subscriptions".
Database unavailable
The database connection is currently unavailable.
Permission denied
The connected database user doesn't have permission to access this table.
Ambiguous query

Ask clarification.

No results
The query executed successfully, but no matching records were found.
